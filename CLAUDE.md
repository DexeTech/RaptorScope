# CLAUDE.md

RaptorScope is a native Win32 + OpenGL 1.1 viewer/editor for Dino Crisis (1999 PC) `.DAT` archives. It covers rooms (RDT), EMD characters, textures, palettes, VAG/SEQ audio, SCD scripts, saves and MPEG video, with OBJ/SMD/GLB export. This repo (`DexeTech/RaptorScope`) is a fork of `coreynguyen/RaptorScope`. Work happens on `dev`, and PRs go to `main`.

[README.md](README.md) is the reference for file formats, SCD opcodes, overlay colours and key bindings. [EXPORTING.md](EXPORTING.md) covers GLB export. [TODO.md](TODO.md) lists unimplemented menu items. Read the relevant README section before changing a parser.

## Build

The live workflow on this machine is MSBuild with the VS project. The project pins toolset `v143`, but only `v145` (VS 18) is installed, so override it:

```powershell
& "C:\Program Files\Microsoft Visual Studio\18\Insiders\MSBuild\Current\Bin\MSBuild.exe" projects\vs2022\DC_Archive_Tool.vcxproj /p:Configuration=Release /p:Platform=x64 /p:PlatformToolset=v145 /m /v:minimal
```

- Output goes to `bin\Release_x64\DC_Archive_Tool.exe`. Linking fails if that exe is still running.
- **MinGW:** run `mingw32-make -f Makefile.mingw` (add `DEBUG=1` for a debug build) from **cmd.exe**, because its `dirs` rule uses `if not exist`. `build-windows.cmd` is a one-shot static build that produces `RaptorScope-DC1-GLB.exe` and the `dc1_export.exe` CLI. MinGW is not installed on this machine.
- **The source list lives in four places:** `Makefile.mingw`, `build-windows.cmd`, `projects/vs2022/DC_Archive_Tool.vcxproj` (plus `.filters`) and `projects/codeblocks/RaptorScope.cbp`. Update all four when you add or remove a `.cpp`.
- `src/formats/emd_glb.inc` is `#include`d at the end of `mesh.cpp`. It is not a separate translation unit.
- `src/ui/about_banner.cpp` is compiled only by the VS project, and nothing references its `vban_data` (M1). The About banner is loaded from RCDATA resource 100 (`res/vban.bin`).
- **Dependencies:** none, by design: only the Win32 API, GDI and OpenGL 1.1 (display lists and immediate mode, no shaders). Do not add libraries. The only exception is `include/ext/pl_mpeg.h`, which is vendored (MIT).

## Architecture

The code is in three layers: `core/` → `formats/` → `ui/`. `core/` and `formats/` don't use Win32. `video.h` is the exception, because it includes `<windows.h>`.

- **`core/`**: shared types (`types.h`), Capcom LZSS (`lzss`), BGR555 colour (`color`), and VAG ADPCM, Gian (SNDH) and SEQ decoding (`audio`).
- **`formats/`:**
  - `dat` is the archive.
  - `texture` does the VRAM deswizzle and the 4/8/16bpp CLUT rendering.
  - `mesh` covers RDT layout, the room/door/EMD parsers, SCD script scanning for the overlay, animation, camera shots and OBJ/SMD/GLB export. It is the core of the reverse-engineering work.
  - `scd` is the disassembler shown in the SCD panel (F4).
  - `tim` handles TIM/IMD images, `save_editor` handles save files and `video` handles MPEG.
- **`ui/`:**
  - `app.cpp` has the window, theme and menus, the archive tree, entry classification and the atlas builder (`upload_archive_texture`).
  - `panels.cpp` has every panel's paint and input code. The largest is `ViewerPanel3D`: rendering, overlay, camera shots, walk mode and picking.
  - `uv_editor.h` and `about_dialog.h` are self-contained, header-only modals.
- `about_audio.h` and `about_banner.cpp` are generated byte arrays. Don't read them.

### Data flow

1. `dat_parse_file` loads the file into `DatArchive::raw`. Each `DatEntry::data` points into that buffer (not owned) unless `owned` is set, which happens after a replace.
2. `App::build_tree` classifies entries. For LZSS0, `classify_lzss0` probes for an RDT scene, a room/door mesh, an EMD, MIPS code or weapon data. Each tree item's `lParam` holds the entry index in its low 16 bits and a sub-selector in bits 16–23: 0 is auto, 1 is the static mesh, and ≥2 is EMD ordinal + 2.
3. `on_entry_select` in `app.cpp` switches on the entry type, fills one of the global panel singletons and calls `switch_panel`. The singletons (`g_hex`, `g_image`, `g_viewer3d`, …) are defined in `app.cpp` and declared `extern` in `panels.cpp`.

### Room pipeline (LZSS0 RDT)

1. `dat_entry_payload` decompresses the entry. ST50B and ST60E store their RDT raw as type 0 (`is_raw_rdt_entry`).
2. `parse_rdt_overlay` walks or scans the SCD and fills `RdtSceneOverlay`.
3. `mesh_apply_xforms` builds **only the sections that scripts place** (0x23, and the item models of 0x28 type-4 zones). Sections that are never placed are appended with `MeshTri::alt = 1`. The viewer hides them unless H is pressed, and GLB export skips them.
4. The code collects each face's tpage and CLUT, then calls `upload_archive_texture` and `set_mesh`. It then calls `overlay_floor_heights` and `set_overlay`, and finally `g_scd.load`.

### PSX conventions used everywhere

- **Load address of an LZSS0 entry:** if `y & 0x8000` is set, `base = ((y & 0x7FFF) << 16) | x | 0x80000000`. Rooms normally use `0x80100000`. Pointers inside the blob minus `base` give file offsets.
- **Viewer coordinates:** `(-x, -y, z)` of game coordinates, which are Y-down. Triangle winding is reversed to match. Angles use 4096 = 360°. One game unit is about 1 mm.
- **tpage:**
  - `tx = tp & 0xF` (in units of 64 halfwords)
  - `ty = (tp >> 4) & 1`
  - `abr = (tp >> 5) & 3`
  - depth = `(tp >> 7) & 3`, where 0 = 4bpp, 1 = 8bpp, 2 = 16bpp
- **CLUT:** `x = (clut & 0x3F) * 16`, `y = (clut >> 6) & 0x1FF`.
- **Atlas:** `ViewerPanel3D::slice_map[row * 65 + slot]` gives a compact slice for each CLUT row. Slot 0 is 8bpp and slots 1–64 are the 4bpp sub-palettes, kept separate so 4bpp and 8bpp never collide.

### Naming traps

The README and the scanners in `mesh.cpp` hold the current understanding of the formats. Some struct names, opcode mnemonics and comments are older and wrong; C1–C6 under Known issues list them. Check those before trusting a name or a comment. The most common trap (C1): `RdtItemSpawn`/`overlay.items` holds 0x5B **enemy spawns**, and `RdtEnemySpawn`/`overlay.enemies` holds 0x42 **objects**.

When you establish a format fact, cite the DINO.exe handler (for example `sub_426806` or VA `0x6576A0`) in a comment, and check it across every room where you can, as existing comments do.

## Code style

- **Language level:** C-style C++, with C++11 as the floor. The UI uses lambdas and `{}` init, despite the README's "pre-C++11" claim. It must build with both MSVC and MinGW and target XP-era Win32 (`WINVER 0x0501`).
- **Containers:** no STL, exceptions or RTTI outside `emd_glb.inc`. Use `Buffer`/`Array<T>` from `types.h` (non-copyable), `malloc`/`free`, fixed-capacity arrays with `MAX_*` constants and `_snprintf`.
- **POD only:** `Array<T>` uses `realloc` and never runs constructors, so `T` must be POD. `RdtSceneOverlay` zero-fills itself with `memset(this, …)`, so keep it POD and bounds-check its fixed arrays.
- **Comments:** follow the existing style: `/*═══…═══*/` file and section banners, `/*─── Name ───*/` sub-headers, and plain-prose comments that say what the game does, with a room as an example.
- **Read-only files:** don't reformat or convert line endings. The index is LF and `core.autocrlf=true`. Don't touch vendored or generated files.

## Commits and docs

- Commit subjects look like `Area: what changed, lowercase` (for example `3D viewer: …`, `Rooms: …`, `Overlay: …`, `GLB export: …`, `README: …`). Bodies are prose: what the game does, which rooms showed the problem, and DINO.exe addresses.
- User-visible features and key bindings go into README.md, usually as a separate `README:` commit. Changes to export behaviour also update EXPORTING.md.

## Known issues

From a full review of the hand-written code on 2026-10-07. The review covered the working tree, including the then-uncommitted overlay and camera-shot work. Generated and vendored files were not reviewed.

Entries are confirmed by reading the code unless tagged **(verify)**. A (verify) entry depends on game data or on how the game behaves, so check it in the viewer or against DINO.exe before changing anything.

**Keeping this list current:**

- **Fixing an entry:** delete it in the same commit and name its ID in the message (`Fixes B3`). If you fix only part of it, rewrite the entry to say what is left. Also search this file for the ID: other sections cite some entries in parentheses, such as (M1) or (T1), and those mentions go too.
- **IDs:** never renumber or reuse them. Add a finding you aren't fixing now with the next free number in its group.
- **Wrong entries:** if an entry turns out to be wrong, delete it and say why in the commit message.
- **Empty groups:** delete a group's heading when it empties, and this whole section when the list is empty.

### Bugs

Ordered with memory safety and data loss first.

- **B2** **UV editor isn't truly modal.** `ShowUVEditor` (`uv_editor.h`) runs its own message loop without disabling the main window, unlike `ShowAboutDialog`.
  - Selecting another entry meanwhile frees `ViewerPanel3D::sel_mask`, which the editor still writes through.
  - File > Exit's `WM_QUIT` is swallowed by the nested loop.
- **B3** **Weapon editor control IDs collide.**
  - Record edits use `9100 + 16*record + field` (fields 6–13) and the aim/camera edits use 9200–9213, so they overlap from record 6 on.
  - `WeaponPanel::save_file` finds aim edits with `GetDlgItem`, which returns the record edit instead. Saving a file with 7 or more records (wep11/wep13 name 13) writes record values into the aim block.
  - The aim values are read every 4 bytes but written back as u16 only, so the high halves are left as they were. (verify the field width)
- **B4** **Save editor out-of-bounds read.** `dc_save_build` indexes its 10-entry digit table with `hours/10`. The Play Time edit has no length limit, so 100+ hours reads past the table.
- **B5** **`new[]`/`free` mismatch.** `parse_standalone_emd_mesh_dec` fills `mesh.verts/tris` with `new[]`, but `Mesh` frees with `free`, and existing arrays are overwritten without being freed. Use `mesh.alloc`.
- **B6** **Dangling pointer after a failed `realloc`.** `mesh_apply_xforms` returns without storing the moved pointer when one of its two `realloc`s fails after the other succeeded. `mesh.verts` or `mesh.tris` is then left dangling.
- **B7** **Audio panel leaks fonts on every repaint.**
  - `paint_wav`, `paint_sndb`, `paint_sndh`, `paint_snde` and the idle branch of `AudioPanel::paint` call `DeleteObject` on fonts that are still selected into the memory DC. The original font is never reselected, so the delete fails.
  - The panel repaints every 33 ms during playback, so GDI handles run out after a few minutes.
- **B8** **WAV buffer leak.** `AudioPanel::load_wav` stores its PCM in `pcm_data`, but `free_samples()` and the destructor free only `samples[i].pcm`.
- **B9** **Script walk stops at 0x01/0x0A.**
  - `scd_opcode_advance` (`mesh.cpp`) treats 0x01/0x0A as script ends and 0x04 as one byte. That contradicts README and `scd_inst_size`.
  - As a result, `parse_rdt_overlay`'s walk misses 0x42/0x20/0x4C/0x2E/0x3A/0x3C/0x3D after them, and the 0x22 adjustment loop in `scan_section_placements` stops early.
  - Fix: switch to `scd_inst_size`.
- **B10** **OBJ/SMD export use the old room builder.**
  - `IDM_EXPORT_OBJ`/`IDM_EXPORT_SMD` call `parse_rdt_scene`, which has its own outdated walker, leaves unplaced sections at raw positions, applies no 0x2A/0x36/0x37 adjustments and puts item models at y=0. They don't use the mesh the viewer shows, which GLB export does.
  - They also LZSS-decompress unconditionally, so ST50B and ST60E can't be exported.
- **B11** **Export dialogs misbehave.**
  - In OBJ/SMD export, cancelling a character's save dialog falls through to the static-mesh path and opens a second dialog; for a child of an RDT scene, that dialog is for the room.
  - With `sub == 0` they try an EMD first, the opposite of `on_entry_select`.
  - Neither success nor failure is reported.
- **B12** **SMD skeleton doesn't line up with the mesh.** `export_emd_smd` writes bone offsets in game axes but vertices in viewer axes (x, y, z negated). Any non-zero bone with parent 0xFF is written with parent 255.
- **B13** **3D view can show stale textures.** `upload_archive_texture` caches the atlas by the `DatArchive*` address plus the CLUT list. `close_archive` doesn't reset that cache and Import/Replace doesn't invalidate it. A reopened archive allocated at the same address, or a replaced texture, can therefore show the old atlas. (likely)
- **B14** **Status bar drops 4 characters of the path.** `App::open_archive` calls `set_status(buf + 18)` five times, but the "RaptorScope - " prefix is 14 characters. The 18 dates from the old title.
- **B15** **Import/Replace and saving leave stale state.**
  - The tree isn't rebuilt, so labels and the `g_emd_info` EMD offsets reflect the old data, and the refresh drops the sub-selector.
  - Save As on an item bank writes the original `raw` bytes, silently dropping any replacements.
  - `dat_write_file`'s result is ignored.
  - `archive->modified` is never checked on close or exit.
  - Ctrl+S (`IDM_FILE_SAVE`) has no handler.
- **B16** **A truncated DAT entry misplaces every entry after it.** `dat_parse_memory` sets `size = 0` for an entry that runs past the end of the file, then advances `data_off` by 0.
- **B17** **Blend modes are approximated wrongly.** `ViewerPanel3D::render` draws ABR 3 (B+F/4) with the same full-additive blend as ABR 1, and ABR 2 (B−F) as a multiply. The comments say quarter-additive and subtractive.
- **B18** **Blending decided from ABR alone (verify).**
  - The viewer (`build_mesh_lists`) and room GLB export (`export_room_glb`) treat ABR 0 as always opaque and ABR 1–3 as always blended.
  - On the PSX, a polygon is only semi-transparent if its command byte also has the semi-transparency bit; for room triangles that is byte +31, which `parse_rdt_layout` reads but no parser keeps.
  - ABR 0 is the 50/50 blend mode, so semi-transparent ABR 0 faces are drawn opaque.
- **B19** **Character GLBs come out tinted.** `export_emd_glb` writes the per-part debug colours (`pcols` from `parse_emd_model_dec`) as `COLOR_0`, and glTF multiplies `COLOR_0` into the base colour. Room GLBs double `avg_colors`, which is already ×1.6, so they mostly saturate.
- **B20** **EMD hierarchies with a parent after its child.**
  - `parse_emd_model_dec` and the bind-pose restore in `anim_select_clip` read `abs_pos[parent]` before it is written when a parent's index is higher than its child's (uninitialised stack).
  - `decode_emd_pose` and GLB export reject such models instead.
  - The bind-pose restore also keeps the last animated frame's normals.
- **B21** **SEQ playback can use the wrong sound bank.** `AudioPanel::render_seq` uses the archive's last SNDB. Archives can hold several SNDH/SNDB pairs, which is why `find_sndb_gian` exists.
- **B22** **SEQ parsers lose sync.**
  - `parse_seq_notes` and `render_seq_to_stereo` skip one byte for 0xAn events, which carry two data bytes.
  - `parse_seq_notes` drops a note that is re-keyed before its note-off; the synth closes it instead.
  - Delta times are read as a single byte. (verify that they aren't variable-length)
- **B23** **Undefined shift in VAG decoding.** `decode_vag_block` shifts by `12 - shift`, which is negative for shift 13–15; the SPU treats those as 9. It also left-shifts negative values.
- **B24** **Mouse and keyboard state is lost.**
  - `Viewer3DProc` uses `LOWORD(lp)` (unsigned) instead of `GET_X_LPARAM`, so captured positions left of or above the window become ~65535.
  - Nothing handles `WM_CAPTURECHANGED`/`WM_KILLFOCUS`, so alt-tabbing during a drag or in walk mode leaves the cursor hidden (the `ShowCursor` count) and walk keys held down.
- **B25** **An empty placed section draws its neighbour (verify).**
  - The one-section loop in `mesh_apply_xforms` `continue`s past an empty header, so the next section is drawn with that placement.
  - Only the Y rotation is applied. The rx/rz values set by 0x23, 0x2A fields 6/8 and 0x37 are ignored.
- **B26** **Zone kind depends on a data byte.** ptr[6] floor zones and 0x28 trigger zones share `RdtSceneOverlay::zones[64]` and are told apart by `flags == 0x28`. Floor zones copy `flags` from data byte +18, so a floor zone with 0x28 there shows as a trigger zone.
- **B27** **Door meshes may render inside out (verify).**
  - `parse_door_mesh_dec` keeps the source winding, while the room parsers reverse it for the same axis flip.
  - Doors render through `set_mesh` with counter-clockwise culling, so their front faces may be culled.
  - `is_door_mesh_entry_dec` also builds the base address without `ex`.
- **B28** **3D atlas palette pairing (verify).** `upload_archive_texture` pairs each texture with the next palette entry and uses `pals[0].vram_x` as the 4bpp base for all of them. The 2D viewer instead finds each face's palette by CLUT position (`render_texture_by_faces`). In 3D, faces whose CLUT lives in a different palette entry get the wrong colours.
- **B29** **UV editor shows the wrong palette rows.** `ShowUVEditor`/`Uve_RebuildTexDib` assume dense rows × sub-palette slices (`slice_h = atlas_h / (rows * subs)`). The atlas is actually the sparse `slice_map` layout with 512-row slices, so P shows the wrong regions when there are several CLUT rows.
- **B30** **Video and audio drift apart (verify).**
  - Frames advance on `SetTimer(1000/fps)`, which is truncated and has about 16 ms granularity, while audio runs on its own clock with no resync.
  - `decode_mpeg_video` doesn't check the first `audio_buf` malloc, and leaks on `realloc` failure.
- **B31** **Latent out-of-bounds reads in texture rendering.**
  - `render_16bpp` takes no buffer size, so `render_texture`'s 16bpp branch can't pass one.
  - `render_4bpp` without deswizzle checks `total_bytes` but not `pix_size`; `render_8bpp` checks both.
- **B32** **Camera-cut table overlap (verify).** `parse_rdt_overlay` reads 17 group descriptors (16 + 17×16 = 288 bytes) but takes zone data from `ptr[2] + 272`, which falls inside group 16.

### Contradictions (code vs README, comments or other code)

- **C1** **Swapped struct names.** `RdtItemSpawn`/`ov.items` holds 0x5B enemy spawns, and `RdtEnemySpawn`/`ov.enemies` holds 0x42 objects.
- **C2** **Wrong opcode names in `g_scd_opcodes` (`scd.h`).**
  - 0x42 `EM_SET` is an object, and 0x5B `ITEM_SET` is an enemy spawn.
  - 0x2A/0x36/0x37 (`UNK_2A`/`SPD_ADD`/`SND_PLAY`) set a work target's field, position and rotation.
  - 0x0C `LOOP_BACK` is README's unconditional jump, and 0x0E `JUMP_REL` its conditional one.
  - `mesh.h` calls 0x3C a light colour, where README and `scd.h` say it is the model slot render mode. `scd.h` calls 0x3D unknown, where the overlay treats it as fog.
- **C3** **Operand decoding in `fmt_operands` (`scd.cpp`) disagrees with the overlay parser and README.**
  - 0x20: position at +4 instead of +8.
  - 0x42: type and id swapped; position at +6 instead of +4.
  - 0x5B: position at +8 instead of +4.
  - 0x3A: the subtype is ignored and xyz is read at +2 instead of +4.
  - 0x37 is shown as a sound.
  - 0x28 type 4 is shown as a door, with a "destination" read from corner bytes.
- **C4** **Three opcode-size tables disagree.**
  - The tables are `scd_inst_size`/`g_scd_opcodes` (`scd.h`), and `scd_opcode_advance` and `opsz` in `parse_rdt_scene_dec` (`mesh.cpp`).
  - They give 0x04 sizes of 4/1/1, 0x0A 4/end/end, and 0x10–0x11 1/0.
  - The 0x28 size table exists three times.
- **C5** **Stale comments.**
  - `mesh.h`'s RDT block calls ptr[0] the "SCD main script table"; it holds lights and ambient.
  - `parse_rdt_overlay` has two stacked banners, one listing ptr[2] as camera data and ptr[4] as door zones.
  - `MeshTri::alt` says "SCD branch variant"; it now means an unplaced section.
  - `ov_draw_zone` calls type 4 a door; it is an item pickup.
  - `mesh_apply_xforms` says it only adds non-zero placements on top of `parse_room_mesh_dec`.
  - `parse_rdt_scene_dec` claims inline sections start at 0x00 and that variants are merged by position; `alternate` is always false.
  - `export_room_glb` says "PSX units"; it writes metres.
- **C6** **Animation comments don't match the code.**
  - The banner above `decode_emd_pose` says the bitstream order is rx, rz, ry, that bytes 0–5 hold the root rotation, and that bones 1..N−1 are encoded. The code reads rx, ry, rz for bones 0..N−1 and ignores bytes 0–5.
  - Its step 4 says local × parent, while the code computes parent × local.
  - The "uv0→idx1, uv1→idx2, uv2→idx0" note in `parse_emd_model_dec` doesn't match the mapping the code uses (uv1→idx0, uv2→idx1, uv0→idx2).
  - The angle-sign flip applied when `n_anim_bones < n_parts` depends on the frame size that `extract_emd_anims` guessed.
- **C7** **Vertex colours are scaled more than README says.** README says 2× (`(tex*vtx)/128`). `avg_colors` (`mesh.cpp`) already multiplies by 1.6 and averages the Gouraud vertex colours into one face colour, and `build_solid_list` then doubles that. The result is about 3.2× and flat-shaded.
- **C8** **Overlay colours don't match README and the legend.**
  - Zone type 3 is drawn mint, but README and the HUD legend say yellow.
  - Floor zones and type-2 zones are both yellow.
  - The legend says lights are gold, but each is drawn in its own colour.
  - The fog rings use `dist_near` as a height around the origin.
- **C9** **Item bank layout is described three ways.** `dat.cpp` says each block is [CLUT][64×152 pixels]; `parse_item_bank` treats it as 128×76; `on_entry_select` says a block's CLUT belongs to the previous item and reads the next block's CLUT, which for the last item is sector padding.
- **C10** **Each decoder handles transparency differently.**
  - README's rule (0x0000 masked, 0x8000 transparent) holds only in the atlas.
  - Elsewhere: `parse_palette` masks only 0x0000; TIM CLUT entries mask 0; TIM 16bpp never masks; IMD masks 0x8000 only and keeps 0x0000 opaque; `render_linear_8bpp` masks index 0.
  - `bgr555_to_rgba` replicates the top bits, while `tim.cpp`, `texture.cpp` and `decode_bgr555` only shift.
  - `parse_palette` followed by `build_palette` turns 0x8000 into 0x0000 and drops STP bits, and `bgr555_to_rgba`'s comment wrongly claims STP sets alpha.
- **C11** **Message text location.** `rdt_extract_text` scans from the highest header pointer, while README and `scd_disassemble` place the text after the last thread in the SCD block. Its `scd_off` is computed and never used.
- **C12** **Docs and names are out of date.**
  - README says the code is pre-C++11, but it uses lambdas and `{}` init.
  - README promises OpenGL 1.1 with a software fallback, but the atlas has non-power-of-two dimensions, which GL 1.1 (GDI Generic) can't texture.
  - README lists `include/ext/ddraw_ext.h`; the actual file is `pl_mpeg.h`.
  - TODO.md lists Import/Replace, PNG export and entry ownership as missing, but all three exist. "Export as PNG" actually writes BMP.
  - The window title and class (`Dino Crisis Archive Tool v2.2`, `DCArchiveToolMain`) and the VS target `DC_Archive_Tool` predate the RaptorScope name.

### Performance and silent limits

- **P1** **Smooth normals are O(V×F).** `mesh_compute_smooth_normals` compares every vertex with every face and runs on every placed room load. It runs before unplaced sections are appended, so those sections get zero normals.
- **P2** **Opening an archive does redundant work.**
  - `App::build_tree` decompresses each LZSS0 entry up to five times: in `is_mips_code`, `parse_rdt_layout_from_entry`, `is_door_mesh_entry`, `is_weapon_data`, and once more for its label.
  - The first texture view runs `collect_texture_usage` on the UI thread, which fully parses every mesh and EMD in the archive (copying data and extracting clips).
- **P3** **The texture atlas is large and handled inefficiently.**
  - It is `width × 512·slices` RGBA and can exceed 100 MB.
  - It is uploaded with `GL_LINEAR`, which blurs PSX textures and bleeds between the stacked CLUT slices; GLB export uses nearest filtering.
  - Its width is never checked against `GL_MAX_TEXTURE_SIZE`, and it is copied a second time into `uv_atlas_rgba`.
  - The viewer also holds each mesh three times: `im_*`, `uv_*` and the caller's copy.
- **P4** **UV editor sort is quadratic.** `ShowUVEditor` uses an O(n²) insertion sort, commented "small N", though rooms have 10K+ faces.
- **P5** **Fixed limits drop data silently.** The limits are:
  - 64 placements/sections (slot masks are u64)
  - 64 zones shared by two kinds (B26)
  - 32 cameras and 16 characters
  - 16 textures and 16 palettes in the atlas and the face-CLUT renderer
  - 16 EMDs per entry, and 64 `g_emd_info` entries (beyond that, selecting EMD n shows EMD 1)
  - a 2000×2000-cell walk grid
- **P6** **VM/software detection misfires on real machines.**
  - It triggers on registry disk names containing "Msft"/"Virtual", and on GL strings containing "D3D" or "Mesa" or vendor "Microsoft" (which GLon12 reports).
  - When it misfires, lighting, culling and textures are turned off.
- **P7** **Walk mode is simplistic.** It keeps a single `walk_floor_y` (no stairs or levels, even though `floor_below` exists for camera shots) and uses a fixed dt of 0.016 s whatever the timer rate.
- **P8** **Save editor setup re-enters the app.** `SavePanel_FinalizeDark` pumps messages from inside `switch_panel` before the save is loaded, so input during its progress popup re-enters the app.
